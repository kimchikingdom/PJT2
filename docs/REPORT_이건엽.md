## 4. 취약점 상세 결과 및 개선방안

### 4.1 소프트웨어 공급망 보안 결함 및 관리 체계 진단 [A03:2025]

**1) 의존성 버전 고정 및 관리 적절성**

- **점검 내용**:
  - 프로젝트 루트 내 `was/requirements.txt` 파일을 확인한 결과, 모든 주요 라이브러리에 대해 `==` 연산자를 사용하여 버전을 특정하고 있음을 확인
  - 이는 공급망 관리 측면에서 **가시성**은 확보되었으나, **'취약점 관리'** 측면에서는 위험 요인이 존재함.


- **분석 결과**:
    ![이미지](images_이건엽/img_4_1_1.png)
  - **Flask 3.1.0**으로 버전이 고정되어 있어, 최신 보안 패치가 포함된 3.1.1 버전이 출시되었음에도 불구하고 시스템이 취약한 상태를 유지하게 되는 **버전 고정의 역설**이 발생함.
  - 고정된 버전 내에 `CVE-2025-47278`과 같은 Critical 취약점이 포함되어 있어, 공급망 실패(AO3)의 직접적인 원인이 됨.


- **개선 방안**:
  - 분기별 의존성 업그레이드 정책
  - 신뢰할 수 있는 공식 소스에서만 패키지 다운로드

---

**2) 알려진 취약점이 있는 패키지 사용 여부**

- **점검 내용**:
  - 자동화 진단 도구인 **pip-audit** 및 **safety**를 활용하여 `was/requirements.txtz`에 명시된 패키지들의 알려진 보안 취약점(CVE) 유무를 전수 조사함.


- **분석 결과**:
    ![이미지](images_이건엽/img_4_1_2_1.png)
    ![이미지](images_이건엽/img_4_1_2_2.png)
  - pip-audit 및 safety 스캔 결과, Flask 3.1.0 버전에서 CVE-2025-47278 취약점이 공통적으로 식별됨.


- **개선 방안**:
  - 분기별 의존성 업그레이드 정책 수립.
  - 신뢰할 수 있는 공식 소스(PyPI 등)에서만 패키지 다운로드 규정화.

---

**3) 의존성 트리의 간접 의존성 파악**

- **점검 내용**:
  - `pipdeptree` 도구를 사용하여 직접 의존성 패키지(Flask 등)가 참조하는 **하위 전이 의존성**(Transitive Dependencies)의 계층 구조와 버전 요구사항을 전수 분석함.


- **분석 결과**:
    ![이미지](images_이건엽/img_4_1_3.png)
  - 분석 결과, **Flask**는 `Werkzeug(3.1.4)`, `Jinja2(3.1.6)`, `itsdangerous(2.2.0)` 등의 핵심 라이브러리에 강하게 의존하고 있음을 확인.
  - 특정 패키지(예: Flask)의 보안 패치를 위해 버전을 수정할 경우, 하위에 연결된 MarkupSafe 등 전이 의존성 패키지들과의 버전 충돌(Conflict) 가능성이 존재함.
  - 직접 의존성뿐만 아니라 간접 의존성 패키지에서 발생하는 보안 취약점 역시 전체 서비스 공급망의 무결성을 해칠 수 있는 잠재적 위협 요인으로 식별됨.


- **개선 방안**:
  - **분기별 의존성 전체 트리 업데이트 및 무결성 검토 정책 수립**: 직접 의존성만 관리하는 방식에서 벗어나, pipdeptree 등을 활용해 전체 트리 구조를 정기적으로 전수 조사하고 패치하는 운영 프로세스 정착.
  - **의존성 고정 최적화**: pip freeze 등을 활용하여 간접 의존성까지 포함된 전체 리스트의 해시(Hash) 값을 관리함으로써 공급망 내 예기치 못한 패키지 변조 방지.

**4) SBOM(Software Bill of Materials) 관리 여부**

- **점검 내용**:
  - 소프트웨어 구성 요소의 투명한 파악 및 관리를 위한 자재명세서(SBOM) 생성 여부와 관리 프로세스를 점검함. 
  - 글로벌 표준 포맷인 **CycloneDX**를 활용하여 서비스 의존성 리스트가 기계 판독이 가능한 형태로 관리되고 있는지 확인.


- **분석 결과**:
    ![이미지](images_이건엽/img_4_1_4.png)
  - cyclonedx-py 도구를 통해 표준 SBOM 파일인 bom.json 생성이 가능함을 확인하였으며, 이를 통해 각 라이브러리의 고유 식별자인 **PURL(Package URL)** 정보를 확보함.
  - 분석 결과, 명세서 내에 취약점이 있는 **flask@3.1.0**이 명확히 식별되고 있음.
  - 현재는 수동으로 생성하는 단계에 머물러 있어, 신규 취약점 발생 시 즉각적인 영향도 파악을 위한 자동화된 중앙 관리 체계가 부재한 상태임.


- **개선 방안**:
  - **SBOM 중앙 관리 및 정기 업데이트**: 빌드 시마다 SBOM을 자동 생성하고 Dependency-Track과 같은 관리 플랫폼과 연동하여 실시간 취약점 모니터링 체계 구축. 
  - **무결성 검증**: SBOM 내 기록된 해시(Hash) 값을 대조하여 공급망 내 라이브러리 변조 여부를 상시 검증하는 프로세스 도입.

### 4.2 Software or Data Integrity Failures [A08:2025]

**1) 배포 단위 체크섬/서명 사용 여부**

- **점검 내용**:
  - 배포 아티팩트(`docker-compose.yml`)가 빌드 서버에서 운영 환경으로 전달되는 과정에서 위변조되지 않았음을 보장하기 위한 **체크섬(Checksum) 생성 및 검증 절차** 존재 여부를 점검함.
  - 임의의 파일 수정 시 해시값이 변하는지 실증하여, 현재 환경에서의 탐지 가능성을 확인함.


- **분석 결과**:
  ![이미지](images_이건엽/img_4_2_1.png)
  - **무결성 기준점 확보**: `shasum -a 256` 명령을 통해 원본 파일의 고유 해시값(`e56d46...`)을 추출함. 
  - **변조 탐지 실증**: 파일 끝에 주석(`# integrity test`)을 추가하는 미세한 변경만으로도 해시값이 `dd0349...`로 완전히 변경되는 것을 확인함. 
  - **위험 요인**: 분석 결과, 배포 시점에 이러한 체크섬을 자동으로 대조하는 **무결성 검증 프로세스가 부재**함. 이로 인해 공급망 중간 단계에서 공격자가 배포 파일을 악성 이미지로 교체하더라도 이를 인지하지 못하고 배포를 강행할 위험이 존재함.


- **개선 방안**:
  - **CI/CD 파이프라인 내 체크섬 자동 검증**: 빌드 시점에 생성된 해시값을 아티팩트와 함께 배포하고, 운영 서버에서 배포 직전 이를 자동 대조하는 스크립트 도입. 
  - **디지털 서명(Code Signing) 적용**: 단순 해시 대조를 넘어, 신뢰할 수 있는 기관의 인증서로 배포 단위에 서명을 수행하여 출처와 무결성을 동시에 보장함.
